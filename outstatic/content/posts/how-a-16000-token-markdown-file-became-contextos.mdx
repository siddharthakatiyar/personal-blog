# How a 16,000 Token Markdown File Became ContextOS

> *A two-month journey from a growing `CLAUDE.md` file to building a local-first context engine for AI coding assistants.*

<Callout type="info" title="Before we begin">
This isn't a launch post.

It isn't an architecture deep dive.

And it definitely isn't a guide on how to build another AI coding tool.

It's the story of how a simple Markdown file slowly convinced me that AI coding assistants were missing an entire layer of infrastructure.
</Callout>

---

## Chapter 1

# The File That Wouldn't Stop Growing

It started with a frustration that probably sounds familiar if you've spent enough time with Cursor.

I'd ask one agent to investigate a bug.

Another would refactor a module.

A third would implement a feature.

Every agent was incredibly capable in isolation.

But none of them seemed capable of **remembering**.

One agent would spend twenty minutes understanding an authentication flow.

The next would rediscover everything from scratch.

A week later, I'd find myself explaining the exact same architectural decision for the third time.

The model wasn't forgetting because it was bad.

It was forgetting because every conversation started from zero.

There was no shared memory.

No accumulated understanding.

No institutional knowledge.

So I did what most engineers do when they don't like a workflow.

I hacked around it.

I created a file called `CLAUDE.md`.

Initially, it contained almost nothing.

A few conventions.

Project structure.

Things future agents should know before touching the repository.

Then I had an idea.

Instead of updating it myself...

why not let the agents update it?

Whenever an agent learned something useful—

a tricky edge case,

an architectural decision,

a convention,

a migration note—

it would append it to `CLAUDE.md`.

The next agent would read it.

Learn from it.

Add something new.

Repeat.

At first, it felt magical.

Every conversation started a little smarter than the previous one.

Instead of repeatedly teaching my AI assistant how the repository worked, I was teaching it once.

Or so I thought.

Weeks passed.

The file kept growing.

500 tokens.

2,000 tokens.

6,000 tokens.

10,000 tokens.

Eventually...

it crossed **16,000 tokens**.

<Terminal title="The evolution of CLAUDE.md">

```text
Week 1    ███
Week 2    ████████
Week 3    ███████████████
Week 5    █████████████████████████
Week 8    ████████████████████████████████████

≈ 16,000 tokens
```

</Terminal>

I had accidentally created something ironic.

The very thing that was supposed to solve the context window problem...

had become another context window problem.

Reading the entire file before every task was becoming expensive.

Important information was buried between historical notes.

Some sections contradicted others.

The larger it became, the less useful it was.

I tried reorganizing it.

Splitting sections.

Removing old entries.

Summarizing previous notes.

Nothing really solved the underlying issue.

The problem wasn't Markdown.

The problem was assuming that **memory is just a document.**

It isn't.

Memory has structure.

Relationships.

Priority.

Freshness.

Relevance.

A note about PostgreSQL indexing shouldn't appear when an agent is debugging CSS.

An authentication flow shouldn't consume tokens during a discussion about Docker.

Everything was technically present.

Almost none of it was contextually relevant.

That's when something clicked.

The real problem wasn't that AI models had small context windows.

The real problem was that I was asking a Markdown file to behave like a retrieval engine.

<PullQuote>

I didn't start building ContextOS because I wanted a better search engine.

I started building it because my Markdown file had become an operating system.

</PullQuote>

That realization completely changed the direction of the project.

I stopped thinking about documents.

I started thinking about infrastructure.

If AI agents were going to become real software engineers, they needed something sitting between the repository and the language model.

Not another vector database.

Not another prompt.

Not another memory file.

Something that could understand a codebase well enough to answer a much simpler question:

> **Given this task, what is the smallest amount of context the model actually needs?**

That question became ContextOS.

Everything else followed from there.

## Chapter 2

# Code Isn't a Document

The obvious solution already existed.

At least, that's what everyone seemed to believe.

Every week another AI infrastructure project appeared with roughly the same architecture.

```
Repository
     │
     ▼
Chunk everything
     │
     ▼
Generate embeddings
     │
     ▼
Vector database
     │
     ▼
Retrieve similar chunks
```

On paper, it made perfect sense.

Take every file.

Split it into chunks.

Generate embeddings.

Store them in a vector database.

Retrieve the most semantically similar pieces whenever an LLM needs context.

For documents, this works remarkably well.

Ask about "database migrations" and you'll probably retrieve documents discussing schemas, indexes, or deployment strategies even if they don't contain those exact words.

Natural language is fuzzy.

Semantic similarity is incredibly valuable.

Code isn't.

---

Imagine asking an agent:

> *"Where is `UserStore` implemented?"*

A human developer doesn't think:

> "Find me something semantically similar to a user storage abstraction."

They think:

> "Find the symbol named `UserStore`."

Exactness matters.

If there are ten authentication systems in a repository, nine of them are noise.

Finding something *similar* is often worse than finding nothing.

It wastes context.

It wastes tokens.

And even worse—

it wastes trust.

The more I thought about it, the more I realized I wasn't building search for English.

I was building search for software.

Software has properties that normal documents don't.

Functions call other functions.

Classes implement interfaces.

Routes invoke middleware.

Configuration values flow through entire execution paths.

Imports connect distant parts of a repository.

Relationships matter just as much as text.

Sometimes even more.

I kept asking myself a simple question.

If a senior engineer joined a project tomorrow, how would they answer questions about the codebase?

They wouldn't read random paragraphs that happened to sound similar.

They'd navigate.

They'd jump to definitions.

Follow imports.

Trace function calls.

Look at implementations.

Expand outward only when necessary.

In other words...

they'd traverse a graph.

---

That realization changed almost every technical decision that followed.

I stopped asking:

> *"How do I retrieve similar text?"*

Instead I started asking:

> *"How would a developer explore this repository?"*

Those are surprisingly different questions.

One optimizes similarity.

The other optimizes understanding.

---

### Choosing BM25 Before It Was Popular

One thing people often assume after hearing about ContextOS is that it started as a vector search engine and gradually evolved into something else.

It didn't.

From the very first prototype, the foundation was built around two ideas:

1. Exact lexical retrieval.
2. Structural understanding of code.

That meant SQLite.

Specifically, SQLite's FTS5 engine.

At first glance, it seemed like an unusual choice.

Around me, every retrieval system was talking about embeddings, ANN indexes, rerankers, hybrid search, and increasingly larger vector databases.

Meanwhile, I was experimenting with...

SQLite.

It sounds almost underwhelming.

But SQLite had something I cared about far more than hype.

It was local.

Fast.

Deterministic.

Zero configuration.

And most importantly—

it excelled at exact symbol retrieval.

If the repository contains `SESSION_ROTATION_MS`, I don't want "configuration related constants."

I want **`SESSION_ROTATION_MS`.**

Immediately.

Without ambiguity.

Without approximation.

Without probabilistic ranking deciding that another constant feels *close enough.*

That decision ended up shaping the entire philosophy of ContextOS.

Not because BM25 is better than embeddings.

It isn't.

They're solving different problems.

Embeddings answer:

> "What looks similar?"

BM25 answers:

> "Where is this thing?"

For code, I found myself asking the second question far more often than the first.

---

### But Search Was Never Going To Be Enough

The first retrieval prototype actually worked surprisingly well.

Queries became dramatically more precise.

Symbol lookup felt instant.

Finding files became trivial.

And yet...

something still felt missing.

Imagine asking:

> "How does authentication work?"

The search engine can find the route.

Great.

But the route immediately calls middleware.

The middleware validates a JWT.

That validator loads configuration.

The configuration references secrets.

The secrets are consumed by another service.

The answer isn't a file.

It's a path.

No search engine could assemble that automatically.

The missing piece wasn't better ranking.

It was relationships.

And that realization led directly to the second major pillar of ContextOS.

Not better search.

A graph.

## Chapter 3

# Software Is a Graph

I used to think retrieval was a search problem.

It wasn't.

It was a navigation problem.

Search tells you **where something is.**

Navigation tells you **how everything is connected.**

That distinction ended up changing almost every part of ContextOS.

---

Imagine asking an AI assistant:

> "How does authentication work?"

A traditional search engine can find every occurrence of the word "authentication."

Maybe it'll return:

- `auth.ts`
- `jwt.ts`
- `middleware.ts`
- `routes.ts`

Technically...

that's correct.

Practically...

it's almost useless.

Authentication isn't a file.

It's a journey.

A request enters the application.

A route calls middleware.

The middleware validates a token.

The validator loads configuration.

Configuration references secrets.

Secrets determine permissions.

Permissions influence database queries.

The answer isn't sitting inside a single chunk.

It's scattered across dozens of small relationships.

That's how software works.

Developers know this instinctively.

When we're trying to understand a new repository, we rarely read files from top to bottom.

We jump.

Definition.

Implementation.

Call site.

Import.

Interface.

Concrete implementation.

Back again.

Every IDE shortcut we use reflects this.

Go to Definition.

Find References.

Peek Implementation.

Call Hierarchy.

We're constantly traversing a graph.

So why was I asking an AI assistant to search flat text?

---

That realization was probably the biggest architectural turning point in the project.

Instead of asking:

> "Which chunks are relevant?"

I started asking:

> "Which chunks become relevant after discovering the first one?"

They're very different questions.

Suppose the initial search retrieves this route:

```ts
router.post("/login", loginUser)
```

A traditional retrieval pipeline might stop there.

Maybe it'll also retrieve a few nearby chunks because they're physically close in the file.

But physical proximity isn't how software is organized.

Software is organized by relationships.

That tiny route immediately tells us new things.

- `loginUser()` is now relevant.
- Whatever `loginUser()` calls is probably relevant.
- Authentication middleware might become relevant.
- Configuration values suddenly matter.
- Session creation becomes important.

The first retrieval doesn't answer the question.

It simply tells us where to look next.

That sounds obvious.

But it completely changes how retrieval works.

---

### Building Relationships

To make that possible, ContextOS needed something more than text indexing.

It needed to understand code.

Not execute it.

Not compile it.

Just understand its shape.

That's where Tree-sitter entered the picture.

Tree-sitter parses source code into an Abstract Syntax Tree—an AST.

Instead of seeing this:

```ts
function login() {
    validateJWT();
}
```

as plain text...

it understands:

- this is a function
- it calls another function
- that function has a name
- that name can be resolved elsewhere

Those relationships are incredibly valuable.

Imports become edges.

Function calls become edges.

Inheritance becomes edges.

Implementations become edges.

Interfaces become edges.

Suddenly the repository isn't just files anymore.

It's a connected graph.

---

### The First Moment It Worked

I'll never forget the first time graph expansion actually worked.

I asked a question.

The initial search returned exactly one chunk.

Then the graph expanded.

One chunk became three.

Three became seven.

Without me explicitly asking for them.

The retrieval wasn't just finding code anymore.

It was following reasoning.

It looked...

intentional.

That was the moment I realized ContextOS wasn't becoming another search tool.

It was becoming something much closer to how developers think.

Not because it was intelligent.

Because it was structured.

---

### Bigger Isn't Better

Around this time I also started noticing another pattern.

Whenever an LLM failed to answer a question, the default reaction was always the same.

Give it more context.

Read another file.

Then another.

Then another.

Soon the model is staring at four thousand tokens of code.

Maybe eight thousand.

Maybe twenty thousand.

Somewhere inside that mountain of text is the answer.

But the model now has another problem.

Finding it.

Humans don't become better engineers by reading more code.

They become better engineers by reading the **right** code.

The same applies to language models.

Retrieval isn't about maximizing context.

It's about minimizing unnecessary context.

Every irrelevant token is competing for the model's attention.

Every unrelated function increases cognitive load.

Every unnecessary file dilutes the signal.

That became one of the guiding principles behind ContextOS.

The goal wasn't to retrieve *more*.

The goal was to retrieve **less**—

while somehow helping the model understand **more**.

---

Everything was finally starting to click.

Exact retrieval found the starting point.

The graph assembled the surrounding context.

The repository was no longer just searchable.

It was explorable.

But a new problem appeared almost immediately.

The first prototype worked beautifully on small repositories.

Then I pointed it at a real codebase.

Fifty thousand files.

Hundreds of thousands of symbols.

Millions of relationships.

Within minutes my laptop fans were screaming.

Memory usage exploded.

CPU usage hit one hundred percent.

And somehow...

I had accidentally spawned enough background processes to nearly bring my Mac to its knees.

For the first time since starting the project, I wasn't thinking about architecture anymore.

I was thinking about beta users.

Because if this happened on my machine...

what was it going to do on theirs?

## Chapter 4

# The Daemon That Tried to Melt My Mac

There's something strangely satisfying about the first prototype of every project.

Everything feels elegant.

The architecture diagram is clean.

The codebase is small.

Benchmarks are fast.

Every idea seems to work.

Then reality shows up.

For ContextOS, reality arrived in the form of a large repository.

Not a toy project.

Not a tutorial.

A real codebase.

Tens of thousands of files.

Millions of lines of code.

The kind of repository AI coding assistants struggle with every day.

The retrieval engine worked.

The graph expansion worked.

The search was surprisingly accurate.

But there was one enormous problem.

Building the index took time.

Lots of it.

---

The simplest implementation looked something like this.

```text
User asks a question
        │
        ▼
Scan repository
        │
        ▼
Parse AST
        │
        ▼
Index symbols
        │
        ▼
Answer question
```

It worked.

Technically.

But nobody wants to wait thirty seconds before asking every question.

The repository doesn't magically disappear between prompts.

Most of it hasn't changed.

So why should ContextOS pretend it's seeing the repository for the first time?

The obvious answer was to keep the index alive.

Instead of rebuilding everything...

build it once.

Watch for changes.

Update only what changed.

Answer instantly.

That decision led to one of the biggest architectural changes in the project.

ContextOS stopped being a command-line tool.

It became two separate programs.

```
            CLI
             │
             │ IPC
             ▼
      Background Daemon
             │
     Watches filesystem
             │
   Incremental re-indexing
```

The CLI became lightweight.

The daemon became responsible for everything expensive.

Watching files.

Parsing syntax trees.

Updating SQLite.

Managing caches.

Keeping the repository "warm."

From the outside it looked simple.

Run a command.

Get an answer.

Underneath...

there was suddenly another application quietly running in the background.

---

### Engineering Is Mostly Edge Cases

The daemon solved performance.

It also introduced an entirely new category of problems.

What happens if the daemon crashes?

How does the CLI know?

What happens if the user opens two terminals?

Three?

Five?

What if they reboot?

What if the PID file says the daemon exists...

but it actually died yesterday?

Windows behaves differently.

macOS behaves differently.

Linux behaves differently.

None of these problems had anything to do with retrieval.

But every one of them affected whether ContextOS felt reliable.

The more I worked on the daemon, the more I realized something.

Infrastructure projects don't fail because their algorithms are weak.

They fail because they're annoying.

Developers forgive slow software.

They don't forgive flaky software.

---

### Then I Almost DOS'd My Own Laptop

One evening I noticed my Mac becoming unusually loud.

The fans were spinning.

CPU usage was climbing.

Everything felt sluggish.

I opened Activity Monitor.

There wasn't one ContextOS process.

There were several.

Then more.

And more.

Somehow I'd managed to spawn multiple background daemons.

Each one thought it was the only daemon running.

Each one was happily watching the filesystem.

Each one was opening thousands of file handles.

Each one was indexing the same repository.

Eventually macOS stopped being polite.

It started throwing:

```
Too many open files.
```

I just stared at the screen.

Not because the bug was difficult.

Because my mind immediately skipped ahead.

I wasn't thinking about my laptop anymore.

I was thinking about the first beta users.

Imagine downloading ContextOS.

Running `contextos init`.

Watching your machine slowly accumulate background processes until your editor stopped responding.

That wasn't a bug.

That was the kind of first impression people never forget.

And probably never forgive.

That moment fundamentally changed how I approached the rest of the project.

I stopped asking:

> "Does it work?"

I started asking:

> "What happens when everything goes wrong?"

---

### Building For Failure

That question slowly found its way into almost every subsystem.

Indexes could be interrupted.

The daemon could crash.

Processes could disappear.

Repositories could contain binary blobs.

Generated files.

Minified JavaScript.

Gigantic vendor directories.

Symlink loops.

Corrupted caches.

Every one of those scenarios eventually became part of the engineering process.

One by one, the codebase accumulated tiny defensive decisions.

Skip binary files.

Ignore generated code.

Throttle concurrency.

Recover stale PID files.

Reconnect automatically.

Incrementally rebuild.

Individually...

none of those features sound exciting.

Collectively...

they're the difference between a demo and a developer tool.

Looking back, I think this was the point where ContextOS stopped feeling like a side project.

It started feeling like software other people might actually depend on.

---

I used to think retrieval accuracy was going to be the hardest part of the project.

It wasn't.

The hardest part was making sure the retrieval engine still worked at two o'clock in the morning...

after the daemon had restarted...

the repository had changed...

the cache had been invalidated...

and the user had absolutely no idea any of that had happened.

Because that's what good infrastructure does.

When it's working...

you almost forget it exists.

And that brought me to the next obsession.

Not performance.

Not architecture.

Not even developer experience.

Measurement.

Because I had reached a point where intuition wasn't good enough anymore.

If ContextOS was going to claim it retrieved better context...

I needed a way to prove it.

## Chapter 5

# You Can't Optimize What You Don't Measure

For a while, I thought ContextOS was doing pretty well.

I'd ask questions.

It would retrieve exactly what I expected.

I'd point it at another repository.

Still looked good.

A few friends tried it.

They liked it.

Everything felt... promising.

There was only one problem.

I had absolutely no way of knowing whether it was actually good.

I was measuring confidence.

Not correctness.

And those two things are dangerously easy to confuse.

---

Every retrieval system looks impressive when you ask it questions you already know the answers to.

You subconsciously phrase prompts the way the system expects.

You know the repository.

You know the filenames.

You know the architecture.

You're unconsciously helping your own software succeed.

That's not evaluation.

That's confirmation bias.

If ContextOS was going to become something other developers relied on, it needed to survive questions written by someone who had never seen the codebase before.

It needed a benchmark.

Not a demo.

Not a screenshot.

A benchmark.

---

### Building an Exam Instead of a Showcase

I started collecting repositories that looked nothing like each other.

A Next.js application.

A FastAPI backend.

Go projects.

Different architectures.

Different coding styles.

Different naming conventions.

Different ways of organizing the same ideas.

The benchmark wasn't designed to prove ContextOS was good.

It was designed to prove me wrong.

Every question had a single purpose.

Could the retrieval engine provide enough information for an LLM to answer correctly...

without reading additional files?

That distinction became incredibly important.

I wasn't benchmarking search.

I was benchmarking **understanding**.

There's a huge difference.

A search engine only has to find a file.

ContextOS had to assemble enough of the surrounding repository that another system—a language model—could reason correctly.

That meant accuracy wasn't enough.

The retrieved context had to be complete.

Compact.

Relevant.

And ideally...

small.

---

### The Hidden Metric Nobody Talks About

Most retrieval papers focus on recall.

How many relevant chunks did you retrieve?

That's important.

But I found myself caring about another number just as much.

Tokens.

Every unnecessary token costs something.

It costs latency.

It costs money.

Most importantly...

it costs attention.

Language models don't magically ignore irrelevant context.

Every extra function.

Every unrelated constant.

Every duplicate snippet.

Every unnecessary import.

They're all competing for the model's limited attention.

Retrieving everything isn't intelligence.

It's laziness.

Good retrieval isn't measured by how much context it returns.

It's measured by how much context it **doesn't** return.

That became one of the hardest balancing acts in the entire project.

Return too little.

The model misses important details.

Return too much.

The signal disappears into the noise.

Somewhere in the middle...

there's a sweet spot.

Finding it became an obsession.

---

### ContextOS Was Winning...

...and I still wasn't happy.

The early benchmark results were encouraging.

The retrieval quality was high.

The graph expansion was working.

Queries that previously required multiple searches could often be answered in one pass.

But something kept bothering me.

Whenever ContextOS missed even a tiny detail, the AI assistant would fall back to reading an entire file.

One missed constant.

One missing helper function.

One truncated section.

Suddenly the model wasn't reading a carefully assembled thousand-token context anymore.

It was reading thirteen thousand tokens from an entire source file.

One tiny retrieval miss had just multiplied token usage by more than ten.

That wasn't acceptable.

Not because the answers became wrong.

Because the retrieval engine had failed its primary job.

It had forced the model to compensate.

Every fallback represented a failure of retrieval.

Not a feature.

---

### Every Miss Became Personal

After that, I stopped looking at benchmark percentages.

I started investigating individual failures.

One question failed.

Why?

Which symbol was missing?

Why wasn't it indexed?

Why wasn't it retrieved?

Why wasn't it promoted?

Was the ranking wrong?

Was the graph incomplete?

Did compression remove something important?

Every miss turned into a debugging session.

Sometimes the answer was embarrassingly simple.

A top-level constant hadn't been indexed.

A filename deserved more weight because the prompt explicitly mentioned it.

A tiny exported variable had been ignored because it looked too small to matter.

Individually...

they seemed insignificant.

Collectively...

they transformed the retrieval engine.

One by one, the benchmark numbers climbed.

Not because I chased percentages.

Because every percentage point represented one fewer moment where another developer would think:

> "Why didn't it find that?"

## Chapter 6

# The Bugs That Made ContextOS Better

By this point, ContextOS had stopped feeling like a side project.

The architecture was stable.

The daemon was reliable.

Benchmarks were finally passing.

Retrieval quality kept improving.

From the outside, it probably looked like the difficult work was over.

It wasn't.

The last ten percent of the project ended up consuming almost half the development time.

Not because new features were difficult.

Because correctness is unforgiving.

---

### The Difference Between "Almost" and "Always"

One thing I learned while building ContextOS is that users don't remember software that works **99%** of the time.

They remember the one time it doesn't.

That one failed retrieval.

That one incorrect answer.

That one repository where nothing works.

Infrastructure software has a much higher standard than application software.

Nobody congratulates your database for returning the correct rows.

They only notice when it doesn't.

I slowly realized that retrieval engines deserve the same expectation.

Every benchmark miss became something I refused to ignore.

---

### The CI Bug That Didn't Exist

One of the strangest bugs appeared after I thought everything was finished.

Every benchmark passed locally.

Every repository.

Every question.

Then GitHub Actions reported complete failure.

Not lower accuracy.

Zero.

After several hours of debugging, I discovered something almost embarrassing.

The daemon wasn't broken.

The retrieval engine wasn't broken.

The benchmark wasn't broken.

My assumptions were.

I had spent weeks testing against repositories that were already indexed.

CI had never seen those repositories before.

The benchmark started asking questions before the daemon had indexed even a single file.

The retrieval engine was behaving perfectly.

It was searching...

nothing.

The fix was almost laughably small.

Instead of assuming indexing had completed, the benchmark simply waited until the daemon explicitly reported that the initial index had finished.

One tiny synchronization bug.

An entire retrieval engine falsely accused.

---

### The Bug That Only Happened In CI

I wish that had been the end of it.

It wasn't.

The benchmark now waited correctly.

And then...

it never finished.

Six minutes.

Still waiting.

No indexing.

No progress.

No errors.

Nothing.

Eventually I discovered something that only appeared inside a completely clean environment.

The daemon was being launched using `npx`.

On my laptop...

that command simply launched the local build.

Inside GitHub Actions...

there wasn't a globally installed ContextOS package.

So `npx` did exactly what it was designed to do.

It attempted to download ContextOS from npm.

Then politely asked:

```
Need to install the following packages?

(y/N)
```

Except there was nobody there to answer.

The CI runner patiently waited forever.

It wasn't a retrieval bug.

It wasn't a daemon bug.

It wasn't even a JavaScript bug.

It was an interactive prompt hidden inside a non-interactive environment.

The fix wasn't complicated.

The lesson was.

Never assume your deployment environment behaves like your development environment.

---

### The Benchmark Was Wrong

The next bug was probably the most frustrating.

ContextOS had clearly improved.

Manual inspection confirmed it.

The retrieved context was correct.

The answers were correct.

Yet the benchmark continued reporting failures.

For several days I chased problems inside the retrieval engine.

Ranking.

Graph expansion.

Compression.

Everything looked fine.

Eventually I did something I probably should have done much earlier.

I questioned the benchmark itself.

It turned out the benchmark harness contained its own bug.

When ContextOS returned a precise range inside a file, the harness inspected only that range.

If it found *some* of the expected information, it stopped reading.

Unfortunately...

the remaining information lived elsewhere in the file.

The retrieval engine had done exactly what it was supposed to do.

The benchmark simply stopped looking too early.

That was a strangely satisfying bug to fix.

Not because it improved the score.

Because it reminded me of something important.

Benchmarks are software too.

They deserve the same level of skepticism as the systems they're measuring.

---

## The NaN That Nearly Broke Everything

Then came my favorite bug.

Not favorite while it was happening.

Favorite in hindsight.

One benchmark suddenly reported something impossible.

Instead of returning roughly a thousand tokens...

ContextOS returned more than **269,000**.

At first I assumed the tokenizer had failed.

Then I suspected compression.

Then graph expansion.

Then SQLite.

Hours later...

the actual culprit turned out to be a single mathematical edge case.

Somewhere inside the compression pipeline, token estimates were calculated using the ratio between the original source length and the compressed source length.

Most of the time...

that worked perfectly.

Except for one scenario.

An empty chunk.

The original length became zero.

JavaScript happily calculated:

```ts
0 / 0
```

Which evaluates to:

```ts
NaN
```

Normally that wouldn't be catastrophic.

Except this particular `NaN` found its way into the global token counter.

Every calculation after that quietly became...

`NaN`.

Eventually the compressor reached its final safety check.

```ts
while (currentTokens > maxTokens)
```

Except `currentTokens` wasn't a number anymore.

It was `NaN`.

And JavaScript has a wonderfully dangerous property.

```ts
NaN > 4000
```

returns

```ts
false
```

The compressor believed everything was fine.

The safety loop never executed.

Every retrieved chunk bypassed compression.

One enormous minified JavaScript file slipped through.

The benchmark exploded.

All because of one division by zero.

The fix?

One line.

```ts
if (originalLength === 0) continue;
```

Sometimes the smallest bugs produce the largest failures.

---

### The Last Few Percent

Looking back, almost none of these bugs were algorithmic.

None of them required a better retrieval model.

None required machine learning.

They required patience.

Reading logs.

Questioning assumptions.

Building better tooling.

Writing better benchmarks.

Running the same experiment hundreds of times.

Eventually something interesting happened.

I stopped thinking of ContextOS as an AI project.

It started feeling much closer to a compiler.

Or a database.

Or a language server.

The goal wasn't to be clever.

The goal was to be predictable.

Deterministic.

Reliable.

Infrastructure.

Ironically, that mindset ended up improving the AI experience far more than any prompt engineering ever did.

Because once the context became reliable...

the models suddenly looked much smarter.

Nothing about GPT changed.

Nothing about Claude changed.

The only thing that changed...

was the quality of what they were allowed to see.

## Chapter 7

# Context Is Infrastructure

When I started building ContextOS, I thought I was solving a problem with AI coding assistants.

Looking back, I don't think I was.

I think I was solving a problem with software engineering.

---

Every few months, language models become dramatically better.

They write cleaner code.

Reason more effectively.

Understand larger repositories.

Support longer context windows.

Each new release makes headlines because the models become smarter.

But after spending two months building ContextOS, I kept arriving at the same conclusion.

Most of the frustrating moments I experienced weren't caused by the model.

They were caused by what the model could—or couldn't—see.

If you ask an engineer to review a pull request without showing them the rest of the repository, they'll struggle.

Not because they're a bad engineer.

Because they're missing context.

If you ask an AI assistant to modify a subsystem while hiding half of its dependencies, it struggles for exactly the same reason.

Again...

not because it's a bad model.

Because it's missing context.

For a long time I blamed the models.

Eventually I started blaming the retrieval.

---

### Bigger Context Windows Aren't The Answer

The obvious response to the context problem has been straightforward.

Just make the context window larger.

32K became 128K.

128K became 1 million.

Eventually we'll probably have models capable of reading entire repositories.

That's impressive.

I'm not convinced it's the right solution.

Software engineering isn't about reading everything.

It's about knowing **what matters right now**.

A senior engineer doesn't mentally load an entire monorepo before changing a button color.

They retrieve information on demand.

They follow relationships.

They ignore irrelevant details.

They're selective.

Ironically, that's exactly what we've spent decades teaching databases, compilers, operating systems, and search engines to do.

Retrieve only what's needed.

No more.

No less.

Why should AI tooling behave differently?

---

### The Repository Already Knows The Answer

One realization kept coming back throughout this project.

Most repositories already contain enough information to answer the majority of engineering questions.

The problem isn't missing knowledge.

The problem is finding the right knowledge at the right time.

Every import.

Every interface.

Every function call.

Every implementation.

Every migration.

Every architectural decision.

It's already there.

The repository isn't lacking information.

It's lacking organization.

The AI doesn't need another explanation.

It needs a guide.

---

### Prompt Engineering Isn't Memory

One thing I find fascinating is how many workflows still revolve around writing increasingly elaborate prompts.

Long system prompts.

Huge instruction files.

Massive `CLAUDE.md` documents.

Project memories.

Global memories.

Custom rules.

I've done all of them.

That's literally how this project started.

But over time I realized something.

Those files aren't memory.

They're documentation.

Documentation is static.

Memory is dynamic.

Documentation grows.

Memory evolves.

Documentation treats everything equally.

Memory constantly decides what deserves attention.

The distinction matters.

Because software engineering isn't just remembering facts.

It's remembering the *right* facts at the *right* time.

### Building Infrastructure Changes How You Think

ContextOS also changed how I think about engineering.

When you're building applications, features are exciting.

Users can see them immediately.

Infrastructure is different.

Success is almost invisible.

Nobody notices when retrieval returns exactly the right symbols.

Nobody tweets about a daemon that never crashes.

Nobody celebrates deterministic ranking.

They simply notice that the AI assistant suddenly feels...

better.

Smarter.

More consistent.

The interesting part is that nothing about the model changed.

Claude didn't become more intelligent.

GPT didn't receive a new reasoning algorithm.

The quality of the context improved.

That's it.

And yet the overall experience changed dramatically.

That still amazes me.

### Open Source Was Always The Goal

People have asked me why I decided to open source ContextOS instead of keeping it private.

The answer is surprisingly simple.

Because the problem wasn't unique to me.

Every developer using AI assistants eventually runs into the same wall.

Conversations disappear.

Context gets fragmented.

Knowledge gets rediscovered.

The same architectural questions get answered over and over again.

I wanted to release something that solved the problem I was personally experiencing.

If it turned out to help other developers too...

that would be the best validation I could ask for.

Open source felt like the obvious path.

Good infrastructure gets better when more people stress it in ways you never imagined.

I'm looking forward to that.

Because I know there are edge cases I haven't discovered yet.

There are repositories I haven't indexed.

Languages I haven't tested.

Workflows I haven't considered.

That's the exciting part.
