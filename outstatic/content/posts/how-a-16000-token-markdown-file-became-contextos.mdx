# How a 16,000 Token Markdown File Became ContextOS

> *A two-month journey from a growing `CLAUDE.md` file to building a local-first context engine for AI coding assistants.*

<Callout type="info" title="Before we begin">
This isn't a launch post.

It isn't an architecture deep dive.

And it definitely isn't a guide on how to build another AI coding tool.

It's the story of how a simple Markdown file slowly convinced me that AI coding assistants were missing an entire layer of infrastructure.
</Callout>

---

## Chapter 1

# The File That Wouldn't Stop Growing

It started with a frustration that probably sounds familiar if you've spent enough time with Cursor.

I'd ask one agent to investigate a bug.

Another would refactor a module.

A third would implement a feature.

Every agent was incredibly capable in isolation.

But none of them seemed capable of **remembering**.

One agent would spend twenty minutes understanding an authentication flow.

The next would rediscover everything from scratch.

A week later, I'd find myself explaining the exact same architectural decision for the third time.

<Notebook date="Week 1">
I'm so tired of copying and pasting the exact same context into every new chat window. There has to be a better way to persist project knowledge across sessions.
</Notebook>

The model wasn't forgetting because it was bad.

It was forgetting because every conversation started from zero.

There was no shared memory.

No accumulated understanding.

No institutional knowledge.

So I did what most engineers do when they don't like a workflow.

I hacked around it.

I created a file called `CLAUDE.md`.

Initially, it contained almost nothing.

A few conventions.

Project structure.

Things future agents should know before touching the repository.

Then I had an idea.

Instead of updating it myself...

why not let the agents update it?

Whenever an agent learned something useful—

a tricky edge case,

an architectural decision,

a convention,

a migration note—

it would append it to `CLAUDE.md`.

The next agent would read it.

Learn from it.

Add something new.

Repeat.

At first, it felt magical.

Every conversation started a little smarter than the previous one.

Instead of repeatedly teaching my AI assistant how the repository worked, I was teaching it once.

Or so I thought.

Weeks passed.

The file kept growing.

500 tokens.

2,000 tokens.

6,000 tokens.

10,000 tokens.

Eventually...

it crossed **16,000 tokens**.

<ClaudeGrowth />

<Notebook date="Week 8">
The agents are reading the file, but they're completely hallucinating. The context window is so polluted with outdated architecture notes from Week 2 that they keep trying to implement a database adapter we deleted a month ago.
</Notebook>

I had accidentally created something ironic.

The very thing that was supposed to solve the context window problem...

had become another context window problem.

Reading the entire file before every task was becoming expensive.

Important information was buried between historical notes.

Some sections contradicted others.

The larger it became, the less useful it was.

I tried reorganizing it.

Splitting sections.

Removing old entries.

Summarizing previous notes.

Nothing really solved the underlying issue.

The problem wasn't Markdown.

The problem was assuming that **memory is just a document.**

It isn't.

Memory has structure.

Relationships.

Priority.

Freshness.

Relevance.

A note about PostgreSQL indexing shouldn't appear when an agent is debugging CSS.

An authentication flow shouldn't consume tokens during a discussion about Docker.

Everything was technically present.

Almost none of it was contextually relevant.

That's when something clicked.

The real problem wasn't that AI models had small context windows.

The real problem was that I was asking a Markdown file to behave like a retrieval engine.

<PullQuote>

I didn't start building ContextOS because I wanted a better search engine.

I started building it because my Markdown file had become an operating system.

</PullQuote>

That realization completely changed the direction of the project.

I stopped thinking about documents.

I started thinking about infrastructure.

If AI agents were going to become real software engineers, they needed something sitting between the repository and the language model.

Not another vector database.

Not another prompt.

Not another memory file.

Something that could understand a codebase well enough to answer a much simpler question:

> **Given this task, what is the smallest amount of context the model actually needs?**

That question became ContextOS.

Everything else followed from there.

## Chapter 2

# Code Isn't a Document

The obvious solution already existed.

At least, that's what everyone seemed to believe.

Every week another AI infrastructure project appeared with roughly the same architecture.

On paper, it made perfect sense.

Take every file.

Split it into chunks.

Generate embeddings.

Store them in a vector database.

Retrieve the most semantically similar pieces whenever an LLM needs context.

For documents, this works remarkably well.

Ask about "database migrations" and you'll probably retrieve documents discussing schemas, indexes, or deployment strategies even if they don't contain those exact words.

Natural language is fuzzy.

Semantic similarity is incredibly valuable.

Code isn't.

---

Imagine asking an agent:

> *"Where is `UserStore` implemented?"*

A human developer doesn't think:

> "Find me something semantically similar to a user storage abstraction."

They think:

> "Find the symbol named `UserStore`."

Exactness matters.

If there are ten authentication systems in a repository, nine of them are noise.

Finding something *similar* is often worse than finding nothing.

It wastes context.

It wastes tokens.

And even worse—

it wastes trust.

The more I thought about it, the more I realized I wasn't building search for English.

I was building search for software.

Software has properties that normal documents don't.

Functions call other functions.

Classes implement interfaces.

Routes invoke middleware.

Configuration values flow through entire execution paths.

Imports connect distant parts of a repository.

Relationships matter just as much as text.

Sometimes even more.

I kept asking myself a simple question.

If a senior engineer joined a project tomorrow, how would they answer questions about the codebase?

They wouldn't read random paragraphs that happened to sound similar.

They'd navigate.

They'd jump to definitions.

Follow imports.

Trace function calls.

Look at implementations.

Expand outward only when necessary.

In other words...

they'd traverse a graph.

---

That realization changed almost every technical decision that followed.

I stopped asking:

> *"How do I retrieve similar text?"*

Instead I started asking:

> *"How would a developer explore this repository?"*

Those are surprisingly different questions.

One optimizes similarity.

The other optimizes understanding.

---

### Choosing BM25 Before It Was Popular

One thing people often assume after hearing about ContextOS is that it started as a vector search engine and gradually evolved into something else.

It didn't.

From the very first prototype, the foundation was built around two ideas:

1. Exact lexical retrieval.
2. Structural understanding of code.

That meant SQLite.

Specifically, SQLite's FTS5 engine.

At first glance, it seemed like an unusual choice.

Around me, every retrieval system was talking about embeddings, ANN indexes, rerankers, hybrid search, and increasingly larger vector databases.

Meanwhile, I was experimenting with...

SQLite.

It sounds almost underwhelming.

But SQLite had something I cared about far more than hype.

It was local.

Fast.

Deterministic.

Zero configuration.

And most importantly—

it excelled at exact symbol retrieval.

If the repository contains `SESSION_ROTATION_MS`, I don't want "configuration related constants."

I want **`SESSION_ROTATION_MS`.**

Immediately.

Without ambiguity.

Without approximation.

Without probabilistic ranking deciding that another constant feels *close enough.*

That decision ended up shaping the entire philosophy of ContextOS.

Not because BM25 is better than embeddings.

It isn't.

They're solving different problems.

Embeddings answer:

> "What looks similar?"

BM25 answers:

> "Where is this thing?"

For code, I found myself asking the second question far more often than the first.

---

### But Search Was Never Going To Be Enough

The first retrieval prototype actually worked surprisingly well.

Queries became dramatically more precise.

Symbol lookup felt instant.

Finding files became trivial.

And yet...

something still felt missing.

Imagine asking:

> "How does authentication work?"

The search engine can find the route.

Great.

But the route immediately calls middleware.

The middleware validates a JWT.

That validator loads configuration.

The configuration references secrets.

The secrets are consumed by another service.

The answer isn't a file.

It's a path.

No search engine could assemble that automatically.

The missing piece wasn't better ranking.

It was relationships.

And that realization led directly to the second major pillar of ContextOS.

Not better search.

A graph.

## Chapter 3

# Software Is a Graph

I used to think retrieval was a search problem.

It wasn't.

It was a navigation problem.

Search tells you **where something is.**

Navigation tells you **how everything is connected.**

That distinction ended up changing almost every part of ContextOS.

---

Imagine asking an AI assistant:

> "How does authentication work?"

A traditional search engine can find every occurrence of the word "authentication."

Maybe it'll return:

- `auth.ts`
- `jwt.ts`
- `middleware.ts`
- `routes.ts`

Technically...

that's correct.

Practically...

it's almost useless.

Authentication isn't a file.

It's a journey.

A request enters the application.

A route calls middleware.

The middleware validates a token.

The validator loads configuration.

Configuration references secrets.

Secrets determine permissions.

Permissions influence database queries.

The answer isn't sitting inside a single chunk.

It's scattered across dozens of small relationships.

That's how software works.

Developers know this instinctively.

When we're trying to understand a new repository, we rarely read files from top to bottom.

We jump.

Definition.

Implementation.

Call site.

Import.

Interface.

Concrete implementation.

Back again.

Every IDE shortcut we use reflects this.

Go to Definition.

Find References.

Peek Implementation.

Call Hierarchy.

We're constantly traversing a graph.

So why was I asking an AI assistant to search flat text?

<RetrievalPipeline />

---

That realization was probably the biggest architectural turning point in the project.

Instead of asking:

> "Which chunks are relevant?"

I started asking:

> "Which chunks become relevant after discovering the first one?"

They're very different questions.

Suppose the initial search retrieves this route:

```ts
router.post("/login", loginUser)
```

A traditional retrieval pipeline might stop there.

Maybe it'll also retrieve a few nearby chunks because they're physically close in the file.

But physical proximity isn't how software is organized.

Software is organized by relationships.

That tiny route immediately tells us new things.

- `loginUser()` is now relevant.
- Whatever `loginUser()` calls is probably relevant.
- Authentication middleware might become relevant.
- Configuration values suddenly matter.
- Session creation becomes important.

The first retrieval doesn't answer the question.

It simply tells us where to look next.

That sounds obvious.

But it completely changes how retrieval works.

---

### Building Relationships

To make that possible, ContextOS needed something more than text indexing.

It needed to understand code.

Not execute it.

Not compile it.

Just understand its shape.

That's where Tree-sitter entered the picture.

Tree-sitter parses source code into an Abstract Syntax Tree—an AST.

Instead of seeing this:

```ts
function login() {
    validateJWT();
}
```

as plain text...

it understands:

- this is a function
- it calls another function
- that function has a name
- that name can be resolved elsewhere

Those relationships are incredibly valuable.

Imports become edges.

Function calls become edges.

Inheritance become edges.

Implementations become edges.

Interfaces become edges.

Suddenly the repository isn't just files anymore.

It's a connected graph.

## Chapter 3.5

# The First Time It Felt Real

I'll never forget the first time graph expansion actually worked.

I wasn't running a benchmark.

I wasn't debugging an indexer.

I just wanted to see if it could answer a question that `CLAUDE.md` failed to answer earlier that week.

I typed in:

> "How does authentication work?"

The system paused.

The initial lexical search found the main `auth.ts` file.

That wasn't surprising. A `grep` search would have done that.

Then, the graph took over.

In the terminal, I watched the logs fly by.

`auth.ts` referenced `validateJWT()`.

The graph walked to `jwt.ts`.

`validateJWT()` referenced `JWT_SECRET` in `config.ts`.

The graph walked to `config.ts`.

`config.ts` imported `DatabaseStore` from `session.ts`.

The graph walked to `session.ts`.

The final output didn't just dump four files onto my screen.

It returned exactly the route, exactly the middleware, exactly the config string, and exactly the session type.

```text
Route
  ↓
Middleware
  ↓
JWT
  ↓
Config
  ↓
Session
  ↓
Database
```

I just stared at my terminal.

I didn't ask for any of those files.

I didn't know the name of the `DatabaseStore` function, and I definitely didn't know where it was defined.

But the engine had figured it out.

Not through a lucky semantic embedding.

Not through an LLM guessing.

Through pure, deterministic structural navigation.

<Reflection>
I didn't just feel like I had built a better search tool. I felt like I had built something that could actually reason about my code the same way I did.
</Reflection>

That was the moment I realized ContextOS wasn't a side project anymore.

It was real.

## Chapter 4

# The Daemon That Tried to Melt My Mac

There's something strangely satisfying about the first prototype of every project.

Everything feels elegant.

The architecture diagram is clean.

The codebase is small.

Benchmarks are fast.

Every idea seems to work.

Then reality shows up.

For ContextOS, reality arrived in the form of a large repository.

Not a toy project.

A real codebase.

Tens of thousands of files.

Millions of lines of code.

The retrieval engine worked.

The graph expansion worked.

But building the index took time.

Lots of it.

Nobody wants to wait thirty seconds before asking every question.

The obvious answer was to keep the index alive.

Watch for changes.

Update only what changed.

Answer instantly.

That decision led to ContextOS becoming two separate programs.

The CLI became lightweight.

A background daemon became responsible for everything expensive.

Watching files.

Parsing syntax trees.

Updating SQLite.

Managing caches.

From the outside it looked simple.

Run a command.

Get an answer.

Underneath...

there was suddenly another application quietly running in the background.

---

### Then I Almost DOS'd My Own Laptop

One evening I noticed my Mac becoming unusually loud.

The fans were spinning.

CPU usage was climbing.

Everything felt sluggish.

I opened Activity Monitor and just stared.

There wasn't one ContextOS process.

There were several.

Then more.

And more.

Somehow I'd managed to spawn multiple background daemons.

Each one thought it was the only daemon running.

Each one was happily watching the filesystem.

Each one was opening thousands of file handles.

Each one was indexing the same repository.

Eventually macOS stopped being polite.

It started throwing:

```
Too many open files.
```

<Notebook date="Week 12">
I'm looking at Activity Monitor and honestly wondering how many beta users would hit exactly the same bug. If this happens on a user's machine on day one, they will never use ContextOS again.
</Notebook>

I wasn't thinking about my laptop anymore.

I was thinking about the first beta users.

Imagine downloading ContextOS.

Running `contextos init`.

Watching your machine slowly accumulate background processes until your editor stopped responding.

That wasn't a bug.

That was the kind of first impression people never forget.

And probably never forgive.

That moment fundamentally changed how I approached the rest of the project.

I stopped asking:

> "Does it work?"

I started asking:

> "What happens when everything goes wrong?"

---

### Building For Failure

That question slowly found its way into almost every subsystem.

Indexes could be interrupted.

The daemon could crash.

Processes could disappear.

Repositories could contain binary blobs.

Generated files.

Minified JavaScript.

Gigantic vendor directories.

Symlink loops.

Corrupted caches.

Every one of those scenarios eventually became part of the engineering process.

One by one, the codebase accumulated tiny defensive decisions.

Individually...

they seemed insignificant.

Collectively...

they're the difference between a demo and a developer tool.

## Chapter 5

# You Can't Optimize What You Don't Measure

For a while, I thought ContextOS was doing pretty well.

I'd ask questions.

It would retrieve exactly what I expected.

I had absolutely no way of knowing whether it was actually good.

I was measuring confidence.

Not correctness.

If ContextOS was going to become something other developers relied on, it needed a benchmark.

Not a demo.

Not a screenshot.

A benchmark.

---

### The Hidden Metric Nobody Talks About

Most retrieval papers focus on recall.

How many relevant chunks did you retrieve?

But I found myself caring about another number just as much.

Tokens.

Every extra function.

Every unrelated constant.

Every duplicate snippet.

Every unnecessary import.

They're all competing for the model's limited attention.

Retrieving everything isn't intelligence.

It's laziness.

Good retrieval isn't measured by how much context it returns.

It's measured by how much context it **doesn't** return.

<TokenComparison />

This became the hardest balancing act in the entire project.

Return too little.

The model misses important details.

Return too much.

The signal disappears into the noise.

---

### The CI Bug That Didn't Exist

Eventually, I reached a point where every benchmark passed on my machine.

I pushed the changes.

I refreshed GitHub Actions expecting green checks.

Everything was red.

Not lower accuracy.

Zero.

For a few minutes, I genuinely questioned everything.

Had I accidentally broken the index?

Corrupted the database?

The answer turned out to be much stranger.

ContextOS wasn't failing.

It was simply...

too fast.

On my machine, every repository had already been indexed dozens of times.

By the time I asked a question, the database was warm.

GitHub Actions had never seen those repositories before.

The benchmark started asking questions before a single file had been indexed.

The retrieval engine wasn't wrong.

It was searching an empty database.

## Chapter 6

# Things I Got Completely Wrong

Readers often assume that open-source projects follow a straight, visionary line from conception to launch.

They don't.

ContextOS is littered with the graves of ideas I was absolutely certain about.

Here are a few things I got completely, spectacularly wrong.

**1. Thinking `CLAUDE.md` was enough.**
I genuinely believed that just giving the model a scratchpad to write on would solve the memory problem. I didn't realize I was just reinventing a very bad, unindexed, flat-file database.

**2. Thinking search solved retrieval.**
I spent weeks optimizing BM25 scoring. I thought if I just ranked the text chunks perfectly, the model would understand the code. It wasn't until I added the AST graph that I realized developers don't search code, they navigate it.

**3. Thinking benchmarks were easy.**
I thought benchmarking was just a matter of running some queries and checking if the files were returned. Building an objective, non-biased test suite that accounted for token efficiency was easily the most difficult engineering challenge of the whole project.

**4. Thinking daemon management was trivial.**
"It's just a background process," I thought. "How hard can it be?" Fast forward to my laptop nearly catching fire because ten ghost daemons were fighting over a SQLite lock.

Every single one of these failures made the final product better.

## Conclusion

# Everything Returns to the Start

If you ask me today what the future of AI coding assistants looks like, my answer is a lot more boring than it was two months ago.

I don't think it's larger context windows.

I don't think it's smarter models.

I think it's better infrastructure.

Because no matter how intelligent an AI agent becomes, it can only reason about the context it is given.

**The repository isn't lacking information. It's lacking organization.**

That's the thesis behind ContextOS.

But if I'm being entirely honest...

I still have a file called `CLAUDE.md` in the root of my repository.

I haven't deleted it.

It's only a few hundred lines now.

It doesn't contain architecture diagrams anymore.

It doesn't contain API routes or database schemas.

It just contains conventions.

Style preferences.

A few quick rules.

Every time I open it, it reminds me that ContextOS didn't start as a retrieval engine.

It didn't start as a graph database.

It didn't start as an infrastructure project.

It started because I got tired of explaining the same thing twice.
